The credibility problem

We've been measuring the wrong things

Activity metrics — screens shipped, interviews conducted, design reviews completed — measure what we did, not what changed as a result. Finance leadership noticed years ago. Now it's time we fix it.

The finance team's actual response

"184 screens shipped. 63 user interviews. 31 design reviews." — "Interesting. And what did that produce for the business?" The silence that followed is why we're here.

The four phases

Where are you on this journey?

The shift from handoff era to design engineering isn't a cliff — it's a progressive arc. Most designers using Cursor and Claude to prototype are already at Phase 3. Phase 4 is the next step, not a leap.

1
Phase 1
Handoff era
Design → gap → code. Figma files, redlines, and the hope that engineering implements it right.
  • Figma, Sketch, Zeplin
  • Spec docs & annotations
  • No codebase access
  • Implementation drift
2
Phase 2
Token era
Design owns the primitive layer. Figma variables map to tokens.json. First token PRs raised.
  • Figma variables → tokens.json
  • Versioned npm package
  • Storybook as bridge
  • First token PRs
3
You are here
Prototype era
Designer inside the stack. Cursor + Claude + git clone. Branch → prototype → PR.
  • Cursor + Claude + IDS
  • Branch → prototype → PR
  • Design review = code review
  • IDS components in real code
4
Destination
Design engineering
Designer = front-end platform team. Owns components, tokens, experiments, and outcomes.
  • Owns component library
  • Design system as infra
  • Visual regression + a11y CI
  • No handoff — ships code

Primary environment
VS Code / Cursor
Your code editor and primary design environment in Phase 4. Cursor's AI (Cmd+I) generates component code from plain English — essential for designers building without full engineering fluency.
Start: Install Cursor. Open IDS repo. Press Cmd+I, describe a component change, review what it drafts.
Component catalog
Storybook
Every IDS component in every state — loading, error, disabled, all variants — documented as code. The Controls panel is a live prop playground that's closer to a design tool than any spec doc.
Start: Run npm run storybook. Find a component. Open Controls. Change a prop. You're operating the real component.
Visual regression
Chromatic
Auto-screenshots every Storybook story on every PR. Flags visual changes for your review. Accepting a diff is your formal design sign-off in the engineering process — automated design QA.
Start: Connect repo at chromatic.com. Raise a PR. Review snapshot diffs — "intentional change" or "regression"?
Token pipeline
Style Dictionary
Transforms tokens.json into CSS custom properties, iOS Swift, Android XML. One source of truth → every platform output. This is the mechanism that makes "designer owns the tokens" structurally real.
Start: Find tokens.json in IDS repo. Run npm run build:tokens. Trace one token from JSON to CSS output.
Feature flags
LaunchDarkly
Ships component changes to a defined % of users without full deployment. Enables A/B tests, gradual rollouts, and one-click rollback. You control exposure from the dashboard — no code deploy needed.
Start: Get dashboard access. Find an existing flag. Read its targeting rules. Toggle it in staging — watch the component switch.
Analytics
Amplitude
Measures what users actually do — funnels, event sequences, A/B results. Define your success metric here before the experiment runs. Never after you see the data.
Start: Find your product's workspace. Locate the funnel for your flow. Identify the event that is your success metric.

Making the case

Realistic ROI is possible —
but it requires the right infrastructure

The "$1 in UX returns $100" era damaged our credibility. Here's how to replace it with evidence that actually holds up in a CFO conversation.

1
Industry statistics
"$1 in UX returns $100." Not your data. Not auditable. Finance has heard it 20 times and stopped believing it 18 times ago.
Credibility: zero
2
Activity output
"We shipped 184 screens, ran 63 interviews." Confuses work with value — accepted only by design teams.
Credibility: internal only
3
Correlation claim
"Revenue rose after the redesign." No control group. Marketing launched a campaign the same week. Correlation without causation.
Credibility: directional only
4
A/B tested impact ← target
"+8.3% completion at 95% confidence." Pre-registered. Your data. Finance can trace the chain from design decision to revenue delta.
Credibility: CFO-level defensible
5
Shared attribution model
Design owns activation/conversion. CS owns retention. Product owns revenue. Each function proves its slice. No zero-sum fight over the same line item.
Credibility: strategically unbeatable
The 6-question credibility test
Is there a before state? Can you compare to a measured baseline? required
Is there a control group? A/B test vs time-series vs anecdote? required
Was the metric pre-registered? Defined before the data was seen? required
Is it your data? Your product's production, not an industry study? required
Is the attribution chain auditable? Can finance trace it? strong signal
Can the claim be falsified? Could the experiment have said "it didn't work"? strong signal

The highest-credibility move you can make

Explicitly separate what you can prove from what you believe but can't yet prove. A design leader who draws this line clearly is far more credible to a CFO than one who claims everything is measurable. Intellectual honesty about measurement limits is itself a trust signal.

Your role evolution

Your role gets more
powerful — not less

Every role in the design org still exists in Phase 4. What changes is what you manage to, how you're evaluated, and the leverage you have. This is an expansion, not a replacement.

The design profession is worth fighting for

The anxiety you're feeling about this shift is real and valid. Learning TypeScript is genuinely hard. A/B tests feel clinical. Code reviews feel exposing. But every Phase 4 competency is learnable — and the AI in your editor carries the syntax while you build the concepts. You are not being asked to become an engineer. You are being asked to work closer to where your decisions actually land.

The alignment discussion

The triad that changes
how decisions get made

In Phase 4, evidence — not role seniority — drives decisions. The experiment result is the authority. Design brings the production signal; PM brings business context; Engineering brings feasibility.

Product Manager
Brings business context
  • Previous experiment results — did it hit the threshold?
  • Business metric that this hypothesis is connected to
  • Rollout risk appetite and timeline
  • Sign-off on success criteria before code starts
Design Lead
Brings production evidence
  • Session replay and funnel data — what's actually failing
  • Hypothesis card (component + change + metric + threshold)
  • DS coverage assessment for this experiment
  • Qualitative signal from flag cohort research
Engineering Lead
Brings feasibility signal
  • DS gap assessment — does IDS have what we need?
  • Flag infrastructure and rollout plan
  • Rollback trigger definition
  • Analytics monitoring ownership during window

The six alignment priorities — in this order

Every triad sync should cover these before anyone opens a Figma file or writes a line of code.

1
Process the previous experiment
Close what's open before opening anything new. Merge, iterate, or discard — document the decision.

Session replay and funnel data — all three look at the same evidence before discussing solutions.

3

E PM

Everyone states out loud: "we agree this succeeds if metric X moves by Y% at 95% confidence." The threshold prevents post-hoc metric selection.

Starting tomorrow

You can start any of
this tomorrow

None of this requires permission, a title change, or a budget. These are things you can do alone, in your next PR, or in your next team meeting.

Day 1 Five things you can do today
1

Run Lighthouse on a production page

Open Chrome DevTools → Lighthouse → Analyze. Note the a11y score. This is your baseline. You now own a number you can improve.

2

Use VoiceOver for 30 minutes

Mac: Cmd+F5. Navigate your product with only keyboard and screen reader. What you experience is what you're shipping to screen reader users today.

3

Open a component source file in VS Code

Clone the IDS repo. Navigate to any component. Read the TypeScript interface. Ask Claude: "explain this prop to me." Start building the mental model.

4

Find one A/B test result in Amplitude

Locate an experiment your team or a neighbouring team ran. Read the result end-to-end. Identify the hypothesis, the metric, the confidence level. This is the language you're learning.

5

Write your first hypothesis card

Pick one component you think is underperforming. Write: "If we change [component] by [change], [metric] will improve by [threshold]." Share it in your next triad sync.

Day 30 Your month-one milestone
→

You've raised a PR that includes Storybook stories

Not just a component change — a component change with a story for each state. Chromatic runs. You review the diff.

→

You've written your first TypeScript interface

Doesn't need to be perfect. string, boolean, a union type. Cursor helped you get there. You understand why it's there.

→

You've read a session replay with a specific question in mind

Not general browsing — you watched 5 sessions looking for a specific friction point in a specific flow. You have an insight ready for the next triad sync.

Day 90 Your quarter-one marker
★

You have an experiment result with a number

One hypothesis shipped to production behind a flag, measured in Amplitude, with a real confidence interval. That number — whatever it is — is your first defensible ROI claim. It's worth more than 200 screens.

The profession is worth fighting for
Design's influence over what ships has always been limited by the distance between where we work and where our decisions land. Phase 4 collapses that distance. The discomfort of learning new tools is the cost of becoming undeniable.
